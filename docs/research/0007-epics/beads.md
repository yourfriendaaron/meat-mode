# Beads epics: model, change signals, viewers

Cluster: beads (gastownhall/beads, `bd` 1.3.2) and other beads viewers. Answers Q1 to Q4 of brief.md for beads only.
Method: shallow clone of tag v1.3.2 into a scratch dir (source read), read-only `bd help ...` run from a non-repo dir, web search. No `bd` command was run against any repo or database. Items marked "not run" are read from source, not observed output.
Grades: A controlled/large n, B single team or small n, C anecdote or opinion, V vendor guidance.

## 1. Epic model (Q1, Q4)

1. Issue types. `internal/types/types.go` (v1.3.2) defines built-in types bug, feature, task, epic, chore, decision, message, molecule, gate, spike, story, milestone, plus an internal `event` type. `bd list --help` lists the filter values as "bug, feature, task, epic, chore, decision, merge-request, molecule, gate, convoy"; custom types are configurable (`types.custom`). Epic is just `issue_type: "epic"`; there is no separate epic table. Q1. Grade V. Read in full (the const block).
2. Parent/child is a dependency edge of type `parent-child` (`types.DepParentChild`). Epic to child, and child to grandchild, use the same edge, so nesting is any depth ("tree of milestones, epics, tasks and subtasks at any depth" per the beads-web entry on beads.gascity.com/community-tools). Q1. Grade V. Highlights only for the community page, source read for the edge.
3. `bd list --json` rows are `IssueWithCounts`: the full issue fields (`id`, `title`, `status`, `priority`, `issue_type`, `assignee`, `owner`, `labels`, `updated_at`, `closed_at`, `close_reason`, `dependencies`) plus `dependency_count`, `dependent_count`, `comment_count` and `parent` (computed from the parent-child edge, omitted when none). Source: `internal/types/types.go` lines 1139-1145, populated in `internal/storage/issueops/ready_work_counts.go` (parent set from a joined column, labels and dependencies from JSON subqueries). Conclusion: one `bd list` call gives type and parent without a per-issue `bd show`. Q1. Grade V. Read in full the struct and the scan function. Not run.
4. Independent confirmation: a third-party viewer's design note, probed against bd 1.1.0, says `bd list --all --limit 0 --json` "carries `parent`, `labels`, and `dependencies` in one call", and that comments need a second call (`bd export`) (https://github.com/halaprix/beads-viewer/blob/main/docs/decisions.md, undated). Q1, Q2. Grade C (one developer's probe, version 1.1.0). Highlights only.
5. `bd show --json` returns `IssueDetails`: issue plus `labels`, `dependencies` and `dependents` (each with dependency metadata including type), `comments`, `parent`. Needed only for descriptions and comments. Source `types.go` line 1149. Q1. Grade V.
6. `bd list` defaults that matter: limit 50 (use `-n 0` for unlimited); closed issues hidden unless `--all` (or `--status closed`); tree output is the default text format, so use `--json` or `--flat`. Wisps (ephemeral), gates, templates and infra beads (agent/role/message) are hidden unless `--include-*`. `--max-rows N` exits 2 if exceeded (circuit breaker). `--brief` drops description, design, notes and similar free text from each row, which cuts payload for a card view. `--skip-labels` skips label hydration (labels then empty), so do not use it when filtering on the `human` label. Source: `bd help list` output, bd 1.3.2. Q1. Grade V. Read in full.
7. Useful filters for the epics view: `-t epic`, `--parent <id>`, `--no-parent` (top-level only), `--exclude-type`, `-l/--label`, `--status a,b` (comma form only, repeating `-s` silently overwrites), `--updated-after`. `bd children <id>` is an alias for `bd list --parent <id> --status all` and includes closed children by default (`bd help children`). Q1. Grade V. Read in full.
8. `bd epic status [--json]`: returns array of `{epic, total_children, closed_children, eligible_for_close}` (`types.EpicStatus`). Implementation `internal/storage/issueops/epic_closure.go`: (a) selects epics where `status != 'closed'` only, so closed epics never appear; (b) skips epics with zero children; (c) children are found only through `parent-child` rows in `dependencies` and `wisp_dependencies` whose target is the epic, i.e. DIRECT children only, not recursive; (d) `closed_children` counts children whose status is exactly `closed`; (e) `eligible_for_close = total > 0 && total == closed`. Q1, Q4. Grade V. Read in full. Not run.
9. Progress semantics (Q4), from (8): closed over all direct children, non-recursive. Deferred, blocked, pinned, in_progress and open children all count as not done but stay in the denominator. A child whose row is missing stays in the denominator (see item 10). Q4. Grade V.
10. Edge case in (8): total is `len(children)` from the dependency rows, closed counts only children whose status row was found and is closed. A dangling edge (child row missing) therefore inflates the denominator. **Inference** from reading the loop; not run. Matters little because bd removes edges on delete, but the viewer should compute its own counts from the list data instead of trusting `bd epic status`.
11. Tombstones: the tombstone/soft-delete system was removed in 0.51.0 (CHANGELOG 0.51.0, 2026-02-16: "Phase 4: Remove tombstone/soft-delete system"). In 1.3.2 `types.go` has no tombstone status. Statuses: open, in_progress, blocked, deferred, closed, pinned, hooked (plus custom). A deleted bead is gone from the database. Q4. Grade V. Highlights of the changelog, grep of source.
12. Assignee is `assignee` (string, omitted when empty); `owner` is the git author email of the creator, not the assignee. Q1. Grade V.
13. Gotcha for the human/project split: epics, children and personal tasks are all ordinary rows; the `human` label is the only separator (labels filter `-l human`). **Inference**: the epics view must read with its own query and the to-do/reminder path must keep filtering on the label, so epics without the label stay out of notifications.

## 2. Change signals for skipping unchanged repos (Q2)

Findings, in order of usefulness for a poller:

1. `bd list --limit 1 --sort updated --json` (reverse order for newest first) or `--updated-after <RFC3339>`. A shipped viewer uses exactly this: "each check is a single `bd list --limit 1`, the full reload runs only when something moved, and nothing polls while every Beads view is hidden" (Beads Dashboard entry, https://beads.gascity.com/community-tools, undated). Q2. Grade C (vendor-listed community tool). Highlights only.
   - Limitation (**Inference**): `updated_at` does not move on delete, and a max-updated check misses a deletion of an older row. Pair it with total count (`bd count` or `bd status --json`) to catch deletes.
2. `bd status --json` returns `summary` counts (open, in_progress, blocked, closed, ready, extended stats) and 24-hour git-history activity (`created`, `closed`, `updated`, `reopened`, `total_changes`). Not a hash, but a cheap counts fingerprint. `bd help status` says it is meant for "fast CI status checks that don't need blocked-count accuracy" and `blocked_count_skipped` exists in the JSON. Q2. Grade V. Read in full help and struct. Not run.
3. Dolt commit hash: the store has `GetCurrentCommit` (used by auto-export to decide whether anything changed: `cmd/bd/export_auto.go` line 72 "storeStateHash — only from store.GetCurrentCommit") but I found no top-level CLI flag that prints it. `bd vc status` shows branch and uncommitted changes; `bd dolt show` and `bd history` exist. Whether `bd vc log` / `bd sql` can print `HEAD` is unverified. Note `--dolt-auto-commit batch` can leave writes uncommitted, so a commit hash is not a complete signal for agents that batch. Q2. Grade V. Highlights of source.
4. Events journal (new in 1.3, `docs/reference/events-journal.md`): `bd events tail --since <seq> [--follow] [--limit N]` prints JSONL records `{seq, ts, op, issue_id, issue}` including `delete` ops, committed in the same transaction as the mutation. Cursor-resumable, so it is the one signal that also catches deletes. Costs: **off by default**, "one snapshot write per mutation", retained 7 days / 100000 rows by default, and it is local to one clone. The doc's warning: every writer (agents, CI, `bd serve`) must have `events-journal: true` or the journal stays empty and "an empty journal is indistinguishable from a caught-up one". Several viewers (beads-web, Beads for Obsidian, beadside) follow it and fall back to polling. Q2. Grade V. Read in full the first 90 lines.
   - **Inference**: turning on the journal in every repo means editing every agent's config; it is a poor first choice for a bridge that must work with repos it does not control. Use the per-repo cheap list check as the default, with the journal as an optional upgrade.
5. `bd export` (JSONL to stdout or `-o`): full dump. Timings from the third-party probe at bd 1.1.0: `export` 328 ms at 29 issues, 1025 ms at 2000 issues, versus `list --all --limit 0 --json` 234 ms and 437 ms respectively (halaprix decisions.md, undated). Not a change signal, but the heavy fallback. Q2. Grade C. Highlights only.
6. `.beads/issues.jsonl` mtime: only exists when `export.auto=true`, which is opt-in since the fix in #4063 (issue #2573 thread: "JSONL auto-export and auto-staging are now opt-in", throttled to once per 60 s per the init docs). Do not rely on it. Q2. Grade V. Highlights only.

Per-call floor: the probe above measured about 130 to 190 ms per `bd` process even for `bd count` on a 2000-issue store (embedded Dolt open). Q2. Grade C. For the target scale (about 1,700 beads over several repos), a full `bd list --all -n 0 --json --brief` per repo is of the order of 0.2 to 0.5 s, so a 60 second poll over a handful of repos is affordable even without a skip signal. **Inference** from the probe; I did not measure 700-bead repos.

## 4. Failures reported by others (Q3)

1. Schema/storage churn. Between v0.49.2 and v0.51.0 (653 commits, 9 releases) beads removed the daemon and RPC, replaced SQLite with Dolt, and removed the JSONL sync layer; one VS Code extension was "completely broken" for >= 0.50 (https://github.com/jdillon/vscode-beads/issues/65, 2026-02-16). Q3. Grade B. Highlights. bv's issue #121 (2026-02-24) is the same story: `bv` showed "No issues found" against Dolt-era `bd`. Q3. Grade B.
2. JSONL stopped being a reliable feed. Auto-export is now opt-in, so file-reading viewers see stale or absent data (issue #2573 thread, assessment after PR #4063, undated). Q3. Grade C. Highlights.
3. Embedded Dolt lock contention with concurrent `bd`. In v1.0.0 a non-blocking flock (PR #2571) made embedded mode single-process: "5 concurrent `bd list` calls would fail 4 immediately" (PR #3005 description, 2026-04-03, from a downstream viewer's report). PR #3005 fixed it by queueing callers with exponential backoff, 50 ms to 2 s, no timeout (waits until context cancel). Q3. Grade B. Read in full the PR text. Consequence for a poller (**Inference**): a read waits behind an agent's write and can take longer than expected; set a command timeout and treat a timeout as "unchanged, retry", not as an error.
4. Silent empty result. Issue #1773 (2026-02-15): `bd list` returned zero rows with a stale `noms/LOCK` file and no error; "makes lock contention appear as data loss". PR #1816 added lock error detection. Q3. Grade B. Highlights. **Inference**: a poller must never replace its stored set with an empty result without checking exit code and stderr; treat "zero rows when the previous poll had many" as suspect.
5. Viewer-side lock contention. beads-ui issue #78 (2026-04-11): "beads-ui background polling contends for embedded Dolt lock and breaks concurrent bd workflows"; another entry says polling "repeatedly touches .beads/last-touched". beads-ui v0.10.0 includes "Avoid concurrent DB access to work around dolt panic". I could not fetch the issue body (crawl timeout). Q3. Grade C. Highlights only.
6. A viewer author's rule from bd 1.1.0 probing: "Never poll `bd`. At 1Hz a `bd count` costs ~13% of a core forever"; "concurrent invocations contend on the write lock... Parallelism buys nothing and costs lock errors", so serialize calls per repo. Q2, Q3. Grade C (one developer, version 1.1.0, numbers pre-date 1.3).
7. Server mode: with an external `dolt sql-server` on the same data dir, `bd` hung with "the database is locked by another dolt process" (issue #1661, bd 0.49.6, Feb 2026; closed as no longer applicable after embedded mode was reworked). In 1.3.x embedded is the default and server mode is opt-in (`bd help dolt`), and there is a `--proxied-server` route. Q3. Grade B. Highlights.
8. Forward schema skew: bd refuses to run against a database written by a newer version ("Schema version downgrade protection", 0.50.0 changelog); `--ignore-schema-skew` proceeds "despite forward schema drift (some queries may fail)" (`bd help list`). **Inference**: a bridge on a different bd version than the agents' will fail with a clear error rather than corrupt data; treat that error as a per-repo "skip and report", and pin the bridge's `bd` to the same binary the agents use.

## 5. Recommendations for the epics reader (all **Inference**, from the above)

1. One call per repo per refresh: `bd list --all -n 0 --json --brief`, filtered in the bridge (types, `parent`, `status`), not `bd epic status` (open epics only, direct children only, no assignee, no child detail). Compute "closed / direct children" yourself from `parent` and `status == closed`. Add `--readonly` so the poller can never write, and `--sandbox`.
2. Skip signal: `bd list --limit 1 --sort updated --json` plus total count from `bd status --json`; full read only when either changes, with a forced full read every N minutes to cover deletes. Use the events journal only where the operator has enabled it everywhere.
3. Guard rails: per-call timeout, one `bd` process at a time per repo, ignore non-zero exits and empty results that follow a large set, and never run it inside the agents' working step cadence faster than once per 30 to 60 s.
4. Show a child's type, priority and assignee from the same list rows (`issue_type`, `priority`, `assignee`); no `bd show` needed.
