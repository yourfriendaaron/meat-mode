## Q1 Obtainium with a GitHub source

1. Release and asset selection. Source: https://github.com/ImranR98/Obtainium/blob/main/lib/app_sources/github.dart (undated, current main; read in full for the selection function). Answers Q1. Grade B (primary source code). Facts from the code:
   - Releases are sorted (default sort `date`; the code's fallback in the fetch function is `smartname-datefallback`), then the first one passing the filters wins.
   - Skipped: drafts always; pre-releases unless `includePrereleases` is on (default false: `value: false`).
   - Within a release, only files that are APK or container files count, then the user's `apkFilterRegEx` is applied. If no APK remains the release is skipped (unless track-only).
   - Version string = `tag_name` (or the release name if `releaseTitleAsVersion` is on). Quote: `targetRelease['version'] = ... targetRelease['tag_name'] ?? targetRelease['name']`.
   - Optional "Verify Latest Tag" uses the release GitHub marks as latest instead of the newest by date.
2. Multiple APKs. Source: https://wiki.obtainium.imranr.dev/sources/ (undated; read in full). Quote: "When more than one APK is available for an app release, the user is prompted to pick one manually... this means the app will not be updated silently in the background". Grade V. **Inference**: publish exactly one APK asset per release (or make the name filterable by a regex), so a one-link add also gets silent background updates.
3. Version comparison. Source: https://wiki.obtainium.imranr.dev/app_tracking/ (already covered by the brief; only extra point). Discussion https://github.com/ImranR98/Obtainium/discussions/1286 (2024-01-14, maintainer, highlights only): the version shown is "just some unique identifier for that release". The wiki says detection works only if both strings share a standard format (`x.y.z`), and a leading `v` and a `-beta` suffix are stripped from the source string. **Inference**: tag `v1.2.3`, versionName `1.2.3` is safe; avoid versionNames with extra suffixes like `1.2.3-dev`.
4. One-link add. Source: https://github.com/ImranR98/Obtainium/discussions/3300 (2026-09-11, maintainer-style answer from reading `interpretLink` and `App.fromJson`; highlights only). Grade C/B. Facts:
   - `obtainium://add/<repo URL>` just opens the add-app page prefilled with that URL (inferred from the answer: "it goes through the `add` action instead, which just opens the add-app page with that URL").
   - `obtainium://app/<JSON>` imports a full config. The JSON itself must follow the path (not a URL to JSON) and needs `id` (package name), `url`, `author`, `name`, and `additionalSettings` as a JSON-encoded string.
   - Easiest way to get a correct one: add the app once by hand, then use "Share app configuration as HTML link", which yields `https://apps.obtainium.imranr.dev/redirect?r=obtainium://app/<encoded JSON>`. This can be published in a README.
   - The Obtainium README (https://github.com/ImranR98/Obtainium, undated, read in full) links "Deep Links - link straight to an import, or add a badge to your own project", but the deep-link doc page itself returned CRAWL_NOT_FOUND on the two URLs I guessed. Gap: I did not read the official deep-links doc.
5. Listing. README says crowdsourced configs live at apps.obtainium.imranr.dev, added by PR to the Obtainium repo (README, undated, full). Grade V. Not needed for a one-link add; a redirect link works without a listing.
6. Signing fingerprint publication. Obtainium's own README publishes package ID plus "SHA-256 hash of signing certificate" (B3:53:...:73:62 for Obtainium), which is the format AppVerifier consumes. AppVerifier (https://github.com/soupslurpr/AppVerifier, undated, full README, 1209 stars) "takes the app's package name and signing certificates hash(es) and compares them to the ones you provided". Command to produce the value: `apksigner verify --print-certs app.apk`. Grade B/V. **Inference**: put package ID and SHA-256 cert fingerprint in the README and each release body.

## Q2 Signing in GitHub Actions

1. Keystore as secret. Source: https://github.com/megamaced/nc_collectives_android/blob/main/docs/SIGNING.md (undated, small project; highlights only). Grade C. Pattern: four secrets (base64 keystore, store password, alias, key password), decoded to `$RUNNER_TEMP` in a step, read by Gradle through env vars; tag build fails if any secret is missing so an unsigned APK can never be published. Quote: "The keystore + passphrase cannot be recovered... a new key has to be issued (which forces users to uninstall and reinstall)". Also chose RSA 4096, validity 36500 days. A second example (https://github.com/KyoMio/CodexMeter, workflow run, undated, highlights) strips whitespace before `base64 -d`, rejects an empty result, uses `fetch-depth: 0`, verifies with `apksigner verify`, deletes the keystore at the end, and marks tags containing `-` as pre-release.
2. Gradle signingConfig vs action vs apksigner. The two examples above sign inside Gradle (`assembleRelease` with env-var signingConfig). A third example uses `r0adkll/sign-android-release@v1` only as a commented-out option (https://github.com/darabo/gap-android/blob/main/.github/workflows/release.yml, undated, highlights). F-Droid says (https://f-droid.org/docs/Reproducible_Builds/, undated, partly read): "It is therefore important that (upstream) developers do the same when signing APKs, ideally by using `apksigner`". Grade V. **Inference**: Gradle's signingConfig calls the same signing library as AGP and is fine; a separate third-party action adds a supply-chain dependency with access to the key, so prefer Gradle signing or a plain `apksigner sign` step.
3. Signature schemes and apksigner. Source: https://developer.android.com/tools/apksigner (undated, highlights). Grade V. `apksigner` supports `rotate` lineage; rotated keys use the v3.1 block on Android 13+ (API 33+) by default, and `--rotation-min-sdk-version 28` extends to 9 to 12L. Corroborated by https://support.doverunner.com/hc/en-us/articles/60228513234457 (vendor article, undated, highlights): build-tools 33+ put rotated key in v3.1, API 28 to 32 see key A. Grade C/V. Zipalign must run before signing.
4. Key change consequences. Android docs (https://developer.android.com/studio/publish/app-signing, undated): "the signing key never changes during the lifetime of your app". SIGNING.md above: installs fail with `INSTALL_FAILED_UPDATE_INCOMPATIBLE` on a different key. Nightshelf workflow comment (https://github.com/Nomadcxx/Nightshelf/blob/2a63756c6443fabd882ade14ffdbedc129f299a5/.github/workflows/release.yml, highlights): a debug-signed release "cannot upgrade one signed with this key, so anyone who installed a debug-signed release has to uninstall". Same warning in https://github.com/ddagunts/pwagen (switching install source with a different key means uninstall plus install). Grade C, consistent.
5. Key backup. No source beyond SIGNING.md ("keep it somewhere safe (password manager)") and IzzyOnDroid's developer-practices index (https://izzyondroid.org/docs/devpractices/, highlights) which links a page on keeping keys safe and notes key rotation is supported at IzzyOnDroid but "not supported" with F-Droid reproducible-build setups. **Inference**: keep the keystore and passwords in two places off the CI (password manager plus an encrypted offline copy), generate the key once, never let the debug key reach a release.
6. Not found: a controlled comparison of r0adkll vs apksigner. Searched, nothing.

## Q3 Versioning, ABI, minSdk

1. versionCode and versionName from a tag. Example in https://github.com/torlando-tech/columba/blob/main/app/build.gradle.kts (undated, highlights; Grade C): `git describe --tags --exact-match`, strip `v`, `versionCode = major*10_000_000 + minor*100_000 + patch*1_000`, fallback to commit count for dev builds. Plugin option: https://github.com/ReactiveCircus/app-versioning ("lazily generating Android app's versionCode & versionName from Git tags", highlights; Grade C). CI examples need `fetch-depth: 0` so tags exist. **Inference**: use a monotonic formula like major*10000+minor*100+patch (fits in int far beyond need) computed in Gradle from the tag, so the same commit always yields the same code (also needed for reproducible builds; IzzyOnDroid rule: build "from a clean tree at exactly the commit your release-tag will point to", https://izzyondroid.org/docs/reproducibleBuilds/RBDevHints/, highlights, Grade V).
2. ABI. A WebView shell has no native code, so ABI splits have no effect; one universal APK is the answer. Per-ABI splits only help NDK-heavy apps (columba and bitchat examples ship ~60 MB per ABI). IzzyOnDroid size rule: ~30 MB per app and per APK (https://izzyondroid.org/docs/general/AppInclusionPolicy/, highlights, Grade V). **Inference** (no source needed): one universal APK also keeps Obtainium to a single asset (see Q1.2). I did not measure a real shell APK size.
3. minSdk. Source: https://commandlinux.com/statistics/android-version-distribution/ (2026-07-31, aggregator of StatCounter April 2026, highlights; Grade C). Cumulative reach: API 26 96.1%, API 28 93.5%, API 29 91.1%, API 30 86.9%, API 33 68.9%. Google's own dashboard page (https://developer.android.com/about/dashboards, updated 2026-10-06) no longer lists platform versions (per https://www.testmuai.com/blog/android-app-testing-device-matrix/, 2026-08, highlights). Reference: UnifiedPush distributor gCompat-UP ships minSdk 7.0 (API 24) and target 17 (https://apt.izzysoft.de/fdroid/index/apk/org.unifiedpush.distributor.fcm, version 2.1.2 dated 2026-09-08, highlights; Grade V). **Inference**: minSdk 26 (Android 8, notification channels are guaranteed, 96% reach) is a defensible floor; 28 if you want v3 signing to be the only scheme on every device. Play target-API rules are irrelevant for sideload, but targetSdk should still track current (37 is out).

## Q4 IzzyOnDroid and F-Droid later

1. **Key finding for the plan.** IzzyOnDroid's policy lists as not accepted: "Apps which are only launching a website inside a webview, and do not offer any significant added value over a browser bookmark, should instead be established as a Progressive Web App" (https://izzyondroid.org/docs/general/AppInclusionPolicy/, undated, highlights; Grade V). **Inference**: a pure WebView shell around a user-chosen URL is at risk of rejection. The native notification-action handling and UnifiedPush are the added value; the app should say so in its listing and keep that code real (not a thin wrapper).
2. IzzyOnDroid other requirements (same page): FOSS licence, release-key-signed APK (no debuggable/testOnly), APK attached to a tagged GitHub/Codeberg/GitLab release (preferred, enables reproducible builds), ~30 MB cap, "trackers (e.g. ads, analytics) are not" tolerated, avoid `usesCleartextTraffic` (use a Network Security Configuration if needed; relevant because hubs may be on HTTP in a LAN), no download of extra executables without opt-in. Izzy signs nothing: "signed by the app's dev team" (FAQ https://izzyondroid.org/faq/, highlights). Reproducible-build hints: LTS OpenJDK 11/17/21, avoid JBR, `temurin` works best in GitHub workflows, keep `META-INF/version-control-info.textproto`, do not let Google re-sign (https://izzyondroid.org/docs/reproducibleBuilds/EstablishApp/ and RBDevHints, highlights; Grade V).
3. F-Droid reproducible builds. https://f-droid.org/docs/Reproducible_Builds/ (undated, partly read; Grade V): F-Droid builds from source, then copies the developer's signature onto its unsigned build; v2/v3 signatures cover all bytes so the APKs "must be completely identical". Timestamps zeroed in AGP 2.2.2+. Obtainium itself is a working example: its README says its signing cert is "also valid for the F-Droid flavour of Obtainium, thanks to reproducible builds" (grade B). The F-Droid-pinned key mechanism `AllowedAPKSigningKeys` is mentioned in SIGNING.md (grade C). Key rotation: IzzyOnDroid supports it, F-Droid reproducible setups do not (devpractices page, highlights).
4. Anti-features from FCM. gCompat-UP (the FCM-based UnifiedPush distributor) is listed at IzzyOnDroid with `NonFreeNet` ("The app connects to Google Servers (Firebase/cloud messaging)") (URL above, 2026-09-08; Grade V). The `embedded-fcm-distributor` library page (https://unifiedpush.org/kdoc/embedded_fcm_distributor/, undated, highlights) says "It doesn't contain any Google proprietary blobs", and "FCM servers can handle webpush requests out of the box, but they require a VAPID authorization". F-Droid's full list: Ads, Disabled Algorithm, Known Vulnerability, Non-Free Addons, Non-Free Assets, Non-Free Dependencies, Non-Free Network Services, No Source Since, Tethered Network Services, Tracking (https://f-droid.org/docs/Anti-Features/, undated, highlights). `Tracking` applies to opt-out analytics or crash reports; proprietary libraries such as Google Analytics keep an app out of f-droid.org entirely. `TetheredNet` does not apply when the server address is configurable, which it is here. ntfy's precedent: a separate F-Droid flavor without Firebase, Google Play flavor with it (https://fotos.esferas.org/docs/subscribe/phone/ mirror of ntfy docs, undated, highlights; Grade V/C). Whether embedded-fcm-distributor alone triggers `NonFreeNet` or is accepted by F-Droid: I found no ruling (gap). **Inference**: if included at all, put it in a separate product flavor so the default build has no FCM code and no `google-services.json`; I did not confirm whether the embedded library needs the developer's own Firebase project (that is Cluster 1 Q3).
5. To keep the door open now: FOSS licence in the repo, one package ID, no analytics or crash-reporting SDKs, no proprietary blobs, builds reproducible from a tag (pinned JDK, pinned Gradle and build-tools, dependency lock or verification metadata), a Network Security Configuration instead of blanket cleartext, Fastlane-style metadata folder, release-key signing from day one with the key you will keep.

## Q5 Size, build and examples

1. Versions. Android Gradle plugin 9.3.0 (July 2026): needs Gradle 9.5.0, SDK Build Tools 36.0.0, JDK 17, max API level 37 (https://developer.android.com/build/releases/gradle-plugin, page dated 2026-07 in its title, highlights; Grade V). JDK 21 is also used in CI examples (CodexMeter) and IzzyOnDroid lists 17 and 21 as supported for reproducible builds.
2. CI without Android Studio. CodexMeter workflow (above): checkout `fetch-depth: 0`, `actions/setup-java` temurin 21, `android-actions/setup-android@v3` with `sdkmanager --install "platforms;android-37.0" "build-tools;37.0.0"`, `gradle/actions/wrapper-validation`, Gradle cache, decode keystore, `./gradlew assembleRelease --no-daemon`, `apksigner verify`, `softprops/action-gh-release@v2`. Grade C, a complete working copy target. Note a Nightshelf comment: Gradle resolves a relative `file()` against the app module, so pass an absolute keystore path.
3. Examples to copy. Small WebView shells with releases and Obtainium links: https://github.com/ddagunts/pwagen (template WebView shell, no Compose/AppCompat, Obtainium install link, highlights). Workflow patterns: Nightshelf, CodexMeter, bitchat-android (per-ABI plus universal assets) above. Production precedent for self-hosted WebView clients (Home Assistant, etc.) is Cluster 2. Not found: a small, well-known WebView-shell app listed at F-Droid whose workflow I could cite; searched once, results were generator tools, not shells.
4. Size: no measured number for a WebView shell. IzzyOnDroid cap is ~30 MB (above).
