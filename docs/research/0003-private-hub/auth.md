# Auth, agent limits and browser hardening (Q3, Q4)

Scope: reader cluster Q3 and Q4 of brief.md. Searched with web_search_exa and web_fetch_exa, 11 calls. Grades: A controlled/large n, B single team/small n, C anecdote/opinion, V vendor guidance. "Highlights" means search highlights only; "full" means fetched page, but truncated at 9000 characters (the two OWASP cheat sheets).

## Q3a. Passkeys / WebAuthn

1. go-webauthn/webauthn is still version 0. README: "This library is still version 0, as per Semantic Versioning 2.0 rules there may be breaking changes without warning." 1347 stars, 15 open issues, BSD-3. Latest release seen: v0.18.2 (19 Sep, 2026 inferred from the page's date order; v0.18.0 is dated 2026-08-27 and has "quite a few breaking changes", with a MIGRATION.md). v0.18.2 fixes: "validate session challenge when finishing ceremonies", "require authorization to initialize uv". Releases are marked immutable. Maintained by one main author. URLs: https://github.com/go-webauthn/webauthn and /releases. Grade V (project's own pages). Highlights only. Answers Q3.
   **Inference:** active and conformance-tested, but a pre-1.0 API that broke in 0.18; pin the version and expect migration work. Challenge-validation fixes in 0.18.2 mean anything older than that should not be used.

2. WebView support exists but only through androidx.webkit. Android docs: "Credential Manager is supported natively in the `android.webkit.WebView` library in version 1.12.0 and later"; call `WebSettingsCompat.setWebAuthenticationSupport(settings, WEB_AUTHENTICATION_SUPPORT_FOR_APP)` after `WebViewFeature.isFeatureSupported(WEB_AUTHENTICATION)`. Dependencies shown: credentials 1.6.0-beta02, webkit 1.14.0 (the Jetpack Webkit overview shows webkit 1.17.1). "The WebKit library doesn't support `mediation:"conditional"` requests" (no autofill-style passkey prompt). https://developer.android.com/identity/sign-in/credential-manager-webview and https://developer.android.com/develop/ui/views/layout/webapps/jetpack-webkit-overview. No dates on pages. Grade V. Highlights only. Answers Q3.
   Also passkeys.dev (2022-09-03, updated since): "WebAuthn is currently not directly supported in embedded WebViews on Android" without extra code; only passkeys for the linked RP ID work in an embedded WebView. https://passkeys.dev/docs/reference/android/ Grade V/C. Highlights only.

3. Blocker for a private hub: passkeys on Android require Digital Asset Links. Android docs: "Using Digital Asset Links is required for passkeys"; the file must be at `https://<domain>/.well-known/assetlinks.json`, HTTP 200, `application/json`, no redirects, with relation `delegate_permission/common.get_login_creds`. https://developer.android.com/identity/credential-manager/prerequisites (V, highlights). Google's Digital Asset Links caching service fetches the file, not the device: a Google engineer's reply on an issue tracker bug, relayed in a Stack Overflow answer (2025), says it "would require the server to be public or at least allow requests from Google's IPs"; observed ranges 66.102.0.0/20 and 74.125.0.0/16, User-Agent "GoogleAssociationService". The same answer covers App Links verification; the passkey path uses the same service per the prerequisites page, but I did not find a source that tests a passkey against a private host directly. https://stackoverflow.com/questions/79696239/ (C, one report; highlights). Android's own App Links page warns not to ship URLs "accessible only with a VPN" (V).
   **Inference:** a tailnet-only or LAN-only hub cannot satisfy the asset-link fetch without opening `/.well-known/assetlinks.json` to the internet (for example a public-facing static host for just that file on the same name, or an allowlist for Google ranges). That is a real conflict with "never reachable from the internet". Unverified: whether an embedded WebView passkey flow actually fails when the association cannot be fetched. Test on a device before committing. Browser (Chrome) passkeys on a private hostname with a valid certificate do not use Asset Links and should work; the problem is the WebView app.

4. Passkeys need a stable RP ID (a hostname). Changing the hub hostname orphans every passkey. Google guidance (V, highlights): keep existing authentication methods (password, 2FA) alongside passkeys during transition. https://developers.google.com/identity/passkeys/developer-guides

## Q3b. Tailscale identity as authentication

5. Serve adds `Tailscale-User-Login`, `Tailscale-User-Name`, `Tailscale-User-Profile-Pic`; "If Serve finds the following headers on an incoming request, it will remove them for security reasons, to avoid header spoofing." Funnel traffic "does not include identity headers". "These identity headers are not populated for traffic originating from tagged devices." Shared-in users are included: "this includes traffic from external users who have accepted a share of your device." Best practice: "only have the service listen on localhost. Otherwise, any user that can call your service directly ... could trivially provide their own values." https://tailscale.com/docs/features/tailscale-serve (V, highlights). Answers Q3 and Q1.
   **Inference:** the headers are only trustworthy when the hub listens on loopback behind Serve. Any second listener (LAN port, container published on 0.0.0.0, a reverse proxy that does not strip them) makes them forgeable. Check the login against an allowlist of one login, and refuse when the headers are absent.

6. Real precedent for header spoofing: TS-2025-002, Tailscale's Grafana proxy did not strip `X-Webauth-*` headers on `/api/` routes, so "members of their [tailnet]" could forge them; patched 15 May 2025. https://tailscale.com/security-bulletins (V, highlights). Also TS-2026-008 (published 2026-10-13): one malformed request could pin a CPU core on a node running Serve or Funnel; fixed in 1.98.9. Same page. Relevance: Serve itself is an attack surface that needs patching.

7. LocalAPI WhoIs alternative: Tailscale's own nginx-auth example calls `WhoIs` on the remote address and rejects tagged nodes (`info.Node.IsTagged()` returns 403) and checks the tailnet name; for shared nodes the tailnet is empty. https://github.com/tailscale/tailscale/blob/main/cmd/nginx-auth/nginx-auth.go (V, highlights). Docs: Tailscale "doesn't provide user identity", it delegates to the IdP and establishes node identity; tagged devices' identity is the tag set. https://tailscale.com/docs/concepts/tailscale-identity (V, highlights).
   Comparable app: OpenClaw gateway lets a verified Tailscale identity satisfy only its WebSocket shared-secret check, verifies with `tailscale whois`, and "does not authenticate HTTP API endpoints"; Funnel needs password auth. https://docs.openclaw.ai/gateway/stable-https-url (C/V, highlights). Pattern: identity header is an additional factor, not the sole one.

8. Gap: I found no Tailscale statement on whether a stolen or malware-controlled tailnet device passes identity auth. **Inference:** it does, since node identity is the credential. Identity auth proves "a device of this user", not "the user at this moment". For an agent-control surface, add a second factor (passkey or password) for the wake-agent action, or accept that tailnet compromise equals hub compromise.

## Q3c. Session lifetime, re-authentication

9. OWASP ASVS 5.0.0: 7.3.1 inactivity timeout and 7.3.2 absolute maximum lifetime, both Level 2, "enforced according to risk analysis and documented security decisions"; 7.2.4 new session token on authentication and re-authentication, terminating the old one (L1); 7.2.3 reference tokens at least 128 bits CSPRNG (L1). https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x16-V7-Session-Management.md (V, highlights).
10. OWASP Session Management cheat sheet: "Common idle timeouts ranges are 2-5 minutes for high-value applications and 15-30 minutes for low risk applications"; absolute 4 to 8 hours for a workday app; enforce server-side; reauthenticate after risk events (new device, password change). https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html (V, highlights).
    **Inference:** the current 90-day cookie is far outside this guidance. A phone app wants long sessions, so split by action: a long session for read, check off, snooze, and a short re-auth window (for example 5 to 15 minutes since last passkey or password check) before enabling Agents on a repo, waking an agent, or changing settings. ASVS gives no number; the number is the operator's documented decision.

11. TOTP as fallback: I did not run a source search on TOTP (RFC 6238) or its Go libraries. Gap. **Inference:** TOTP adds a shared secret on the hub and a code to type on the phone; against a stolen session cookie it does nothing unless it gates the sensitive actions; against an attacker on the tailnet with the password it is the second factor. A passkey is stronger and simpler if item 3 is solved.

## Q3d. Limiting what the hub can make agents do

12. Lethal trifecta (Simon Willison, 2025-06-16): "Access to your private data", "Exposure to untrusted content", "The ability to externally communicate in a way that could be used to steal your data". "removing any one of those three legs is enough to prevent the attack" (talk write-up, 2025-08-09). He adds the trifecta is about theft; tool calls that cause damage without leaking data are "a whole other set of problems". https://simonwillison.net/2025/jun/16/the-lethal-trifecta/ and https://simonwillison.net/2025/Aug/9/bay-area-ai/ (C, expert opinion widely cited; highlights). Also 2023-12-20: assume untrusted text "will be able to subvert your instructions and ... trigger any sort of actions that you've made available" (C).
    **Inference:** task text and notes are written by the user, by other agents, and by anything that can reach the hub, so they are untrusted content. A coding agent on the user's machine has private data (source, credentials in the environment) and network access: all three legs. The hub should cut the leg it can: who may write task text (authenticated user only, agents' own tasks labelled), and the agent's exfiltration path (sandbox network allowlist).
13. OWASP LLM01:2025: "it is unclear if there are fool-proof methods of prevention for prompt injection"; mitigations include "Enforce privilege control and least privilege access", "Require human approval for high-risk actions", "Segregate and identify external content". https://genai.owasp.org/llmrisk/llm01-prompt-injection/ (V, highlights). OWASP LLM prompt injection cheat sheet: approval must be for "the exact action", and approval fatigue is a risk: "prone to get user fatigue when constantly being prompted". https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html (V, highlights).
14. Claude Code controls (V, Anthropic docs, highlights): permission rules evaluate "deny, then ask, then allow", first match wins; "Permission rules are enforced by Claude Code, not by the model"; deny rules apply in every mode including bypassPermissions. `auto` mode: "a background classifier checks that they align with your request" (a second model, not a deterministic rule). `dontAsk` auto-denies anything not pre-approved and suits "Locked-down CI and scripts" (with `-p ... --allowedTools "Bash(npm test)" "Read"`). `permissions.disableBypassPermissionsMode` and `permissions.disableAutoMode` can be set to "disable" in managed settings. Sandbox: "sandbox restrictions still apply even if a prompt injection bypasses Claude's decision-making"; it is OS-enforced, covers Bash/PowerShell/Monitor and children only, "Claude's file tools, MCP servers, and hooks run outside it"; off by default (`sandbox.enabled`). https://code.claude.com/docs/en/permissions , /permission-modes , /sandboxing .
    **Inference:** the strongest set for hub-woken runs is `dontAsk` with an explicit allowlist per repo, deny rules for network tools and secrets paths, the OS sandbox on with a network domain allowlist, and `disableBypassPermissionsMode`. `--permission-mode auto` trades that for convenience: its guard is a model that reads the same injected text. The classifier's miss rate is not stated in what I read (gap). Option cost: `dontAsk` means tasks needing an unlisted command fail instead of asking; a human-confirm route (agent machine prompt, or the hub showing the pending action) restores them.
15. Human confirmation on the agent machine: no source found on a ready-made pattern for out-of-band confirmation of an agent wake. **Inference:** the useful split is two kinds of request. "Do this task" from the app on an already-enabled repo could run under the restrictions in 14. "Enable Agents on a repo", "widen an allowlist", or a first wake after a long idle should need a local confirmation on the agent machine or a fresh passkey, because they widen what a hub compromise can do.

## Q4. Browser-side hardening

16. CSP (OWASP CSP cheat sheet, full up to the truncation point): strict CSP via nonce or hash; "Using a header is the preferred way"; meta tag cannot do "framing protections, sandboxing, or a CSP violation logging endpoint"; `frame-ancestors` obsoletes X-Frame-Options; Report-Only first. https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html (V). **Inference:** a vanilla TS bundle with no inline script can use `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` with no nonce machinery. Inline style attributes in the DOM would need `style-src-attr` care; check by running Report-Only against the e2e suite.
17. HTTP headers cheat sheet (full up to truncation; V): `Referrer-Policy: strict-origin-when-cross-origin` set explicitly; `X-Content-Type-Options: nosniff`; `X-XSS-Protection: 0`; `Cache-Control: no-store` for sensitive responses (and the Cache API ignores HTTP caching headers, so a service worker must not cache API responses); CORS: if unused, same-origin policy protects by default, and `*` only for public APIs; COOP isolates the browsing context group. https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html. Permissions-Policy section was past my truncation: not read. **Inference:** send no CORS headers at all, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, and `Permissions-Policy` denying camera, microphone, geolocation, payment, usb. HSTS is only safe if the certificate will not lapse; Serve's managed certificates make that low risk, a LAN self-signed setup makes it risky.
18. Cookies (MDN, highlights): `__Host-` requires `Secure`, a secure page, no `Domain`, `Path=/`; "as close as can be to treating the origin as a security boundary". `__Host-Http-` additionally requires HttpOnly. MDN recommends `__Host-` for single-host cookies, HttpOnly for session IDs, Strict or Lax SameSite, and Max-Age over Expires. Prefix is ignored by browsers that lack support. https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie and /Web/Security/Practical_implementation_guides/Cookies . Server must check the full name including prefix. **Inference:** `__Host-Http-session; Secure; HttpOnly; SameSite=Strict; Path=/`. Catch: `Secure` cookies need HTTPS, except localhost. A plain-HTTP LAN deployment cannot use the prefix. Another catch: the Android WebView must load the https URL.
19. CSRF (OWASP cheat sheet, highlights): `Sec-Fetch-Site` is "the primary signal"; "a fallback to standard origin verification headers is a mandatory requirement for any Fetch Metadata implementation"; supported in all major browsers since March 2023. https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html . ASVS 5.0 3.5.1 to 3.5.3 (L1): validate origin or use non-safelisted headers/anti-forgery tokens; state changes on POST/PUT/PATCH/DELETE, not GET; 3.5.2 if relying on CORS preflight, check Origin and Content-Type so no request avoids preflight. https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md (V, highlights).
    **Inference:** the hub's existing Host/Origin/Sec-Fetch-Site/Content-Type checks already meet these. "Beyond Origin": require a custom header such as `X-Requested-With` or a JSON content type on every state change (forces preflight), and make sure no state-changing GET exists. A per-session CSRF token adds little with SameSite=Strict plus these. Reject a request with no Origin and no Sec-Fetch-Site on state changes, except from the bridge (which does not use cookies).
