# Q1: Network boundary detection

Scope: how a Go server can tell "private network" from "internet". 11 tool calls (search plus fetch), then stop; the last sources repeated earlier ones.
Grades: A controlled/large n, B single team or small n, C anecdote/opinion, V vendor guidance. "Full" = page read in full, "HL" = search highlights only.
Dates: Tailscale and Caddy/Traefik docs are undated pages; "validated" dates are quoted where shown.

## Bottom line (all **Inference**)

1. No single signal proves "private". Each technique proves one narrow fact, and each has a deployment shape that silently defeats it. Layer them and fail closed.
2. The strongest positive proof when the hub sits behind Tailscale is to ask the Tailscale daemon (WhoIs) about the TCP peer, or to read Serve identity headers while listening on loopback only. Both prove "a tailnet node made this connection". Both fail for non-Tailscale private access (LAN, other VPN).
3. Source-address classes are a weak check. Go's own maintainers say `IsPrivate` is not a security property. Use it only on the direct TCP peer, never on a header value, and only after you know no local proxy rewrites the peer.
4. The most dangerous failure is the fail-open one: a same-host proxy (cloudflared, Caddy, Serve itself, rootless podman forwarding) makes every internet request look like loopback or like a private gateway address. A "private peer means trusted" rule then admits the internet.
5. A startup DNS check is useful but only catches misconfiguration at one moment. Funnel records can appear later and linger after Funnel is off.

## 1. Tailscale Serve, Funnel and the identity headers

- Serve adds `Tailscale-User-Login`, `Tailscale-User-Name`, `Tailscale-User-Profile-Pic` for tailnet traffic. Funnel traffic "does not include identity headers". If Serve finds those headers on an incoming request it removes them "to avoid header spoofing". Non-ASCII values may be RFC 2047 Q-encoded. Identity headers are "not populated for traffic originating from tagged devices". They are populated for external users who accepted a share of your device. Source: https://tailscale.com/kb/1312/serve (and https://tailscale.com/docs/features/tailscale-serve), undated. Answers Q1, Q3. Grade V. HL.
- Vendor guidance on spoofing: "best practice to only have the service listen on localhost. Otherwise, any user that can call your service directly ... could trivially provide their own values". Listening only on localhost "limits tampering to only other services running on the Serve device, and not anyone on your LAN or tailnet". Same URL. Q1. V. HL.
- Source code (main branch) of `addTailscaleIdentityHeaders` in `ipn/ipnlocal/serve.go`: it first deletes `Tailscale-User-Login`, `-Name`, `-Profile-Pic`, `Tailscale-Funnel-Request`, `Tailscale-Headers-Info` from the inbound request; then if the connection is a Funnel connection it sets `Tailscale-Funnel-Request: ?1` and returns; otherwise it calls `WhoIs` on the source address, returns with no identity headers if the source is not a tailnet node ("traffic from outside of Tailnet (funneled or local machine)") or the node is tagged, else sets the three identity headers and `Tailscale-Headers-Info`. `addProxyForwardedHeaders` also sets `X-Forwarded-For` to the source address, `X-Forwarded-Host`, and `X-Forwarded-Proto: https` when TLS. URL: https://github.com/tailscale/tailscale/blob/main/ipn/ipnlocal/serve.go . Q1. Grade B (primary source, vendor code). HL.
- Earlier commit (June 2023, v1.44) confirms the strip-then-set order and "headers are passed through empty when the request originated from another tailnet, or the public internet (via funnel)". https://gitea.codinget.me/webnet/tailscale/commit/e1cdcf770803090d1dd451e4c748792082eb1fec.patch (mirror); release note in https://github.com/tailscale/tailscale/issues/6954 (closed 2023-06-22). Q1. B. HL.
- Third-party confirmation that the marker is `Tailscale-Funnel-Request: ?1`, and that a managed Funnel hostname reached from inside the tailnet arrives WITHOUT the marker (it takes the Serve identity path). An app that treats "no marker" as private is wrong on that hostname if the same name is publicly reachable by another path. https://github.com/openclaw/openclaw/pull/126519 (undated). Q1. C. HL.
- Serve and Funnel share a port exclusively: "If the most recent command to configure the port was `serve`, then the port will be completely private. If ... `funnel`, ... completely public." Funnel only on 443, 8443, 10000, only `*.ts.net` names, TLS only. https://tailscale.com/kb/1223/funnel (validated Jan 20, 2026). Q1. V. Full.
- Funnel hides the node address: relay terminates nothing, "creates a TCP proxy to your device over Tailscale"; Tailscale's daemon terminates TLS and hands plain HTTP to the local service. Same page. Q1. V. Full.
- Serve proxy targets: "only `http://127.0.0.1` is supported for proxies" (docs) and the Services PR says the localhost restriction applies to services too. https://tailscale.com/kb/1242/tailscale-serve (validated Jan 26, 2026); https://github.com/tailscale/tailscale/pull/16191 (2025-06-04). Q1. V/B. Full / HL.
- PROXY protocol: `tailscale serve --proxy-protocol=2 --tls-terminated-tcp=443 tcp://127.0.0.1:PORT` gives the backend "the original source IP and port" (TCP mode only). Same kb/1242 page. Q1. V. Full.

What breaks the header technique (**Inference** from the above):
- Backend bound to anything but loopback: any LAN or tailnet peer sets the headers itself. Docker or podman publishing the hub on `0.0.0.0` does exactly this.
- Any other process on the same host can still forge the headers (docs say so). Another same-host proxy in front of the hub (Caddy, cloudflared) that forwards client-supplied `Tailscale-*` headers re-opens the hole unless it strips them.
- Absence of `Tailscale-Funnel-Request` proves nothing: plain local connections, other proxies and tailnet access to a Funnel hostname all lack it. Test for presence of valid identity, not absence of the marker.
- Tagged nodes, nodes in other tailnets and shared-in users: tagged gets no identity, shared-in users get their own identity. "Header present" is not "owner".
- Funnel is also a different threat shape: the request is internet traffic, comes through the same loopback hop, and nothing but the one marker header distinguishes it from a local call.

## 2. tsnet and LocalAPI WhoIs

- `lc.WhoIs(ctx, r.RemoteAddr)` returns the owner of a peer address; "If not found, the error is ErrPeerNotFound"; stable API. `WhoIsProto` pins tcp or udp. https://pkg.go.dev/tailscale.com/client/local , https://pkg.go.dev/tailscale.com/tsnet (both undated). Q1. V. HL.
- Quote from a Tailscale engineer (2023-03-08): WhoIs "only wants a Tailscale IP or a localhost:port of a TCP src that tailscaled itself initiated to localhost when proxying an incoming connection. Any other form of IP won't work." So WhoIs on a LAN address errors. Loopback needs the port. https://github.com/tailscale/caddy-tailscale/issues/12 . Q1. B. HL.
- tsnet embeds a node in the process (gVisor netstack). `srv.Listen` receives only tailnet connections; `ListenFunnel` is the only public path and has `FunnelOnly()`. `ListenService` needs a tag-based identity. https://github.com/tailscale/tailscale/blob/main/tsnet/tsnet.go . Q1. V. HL.
- **Inference**: an in-process tsnet listener is the one design where "the socket only accepts tailnet traffic" is a property of the code, not of a firewall or proxy. There is no Docker NAT, no loopback hop. Cost: a Tailscale dependency in the hub, a tailnet auth key, and no LAN-only mode.
- Break cases: the hub must reach the local tailscaled (socket path in a container); WhoIs via the host daemon only works for connections the daemon proxied, so it fails if a different proxy sits between; a tagged node still returns a node but no user.

## 3. Tailscale Services (VIP services)

- A Service has "a stable TailVIP, unique MagicDNS name", an IPv4 and IPv6 pair. Hosts must use "a tag-based identity". `tailscale serve --service=svc:NAME --https=443 127.0.0.1:8080`; runs in background; needs admin approval. https://tailscale.com/docs/features/tailscale-services ; https://tailscale.com/blog/services-beta (2025-10-28). Q1. V. HL.
- Layer 7 endpoints "work well when you need Tailscale to inject authentication headers". Source: `webServerConfig` and the HTTP handler take the same path with `ForVIPService` set, so the identity-header code above applies. Q1. V/B. HL.
- **Inference**: Services change the address clients dial (a VIP, not the node IP) but not the trust model. Same loopback-only backend rule applies. TailVIPs sit in the CGNAT/ULA classes, so address-class checks treat them as Tailscale.

## 4. Address classes in Go

- `netip.Addr.IsPrivate`: true for the three RFC 1918 ranges, the ULA range (RFC 4193). "IsPrivate does not describe a security property of addresses, and should not be used for access control." https://pkg.go.dev/net/netip (2026-10-08). Q1. V. HL.
- Tailscale uses CGNAT the RFC 6598 shared range (excluding a ChromeOS slice of it used by ChromeOS) and the ULA prefix Tailscale's ULA /48; the node-local services are Tailscale's in-tailnet resolver address and an address in it; via-routes use a /64 inside it. https://tailscale.com/docs/reference/reserved-ip-addresses (validated Jan 12, 2026); `tsaddr.IsTailscaleIP` in https://github.com/tailscale/tailscale/blob/main/net/tsaddr/tsaddr.go . Q1. V/B. HL.
- `IsPrivate` returns false for the RFC 6598 shared range. Go maintainer neild (2025-11-08, issue 76067): "From what I've seen, `IsPrivate` was a mistake. Just about every use of it ... declaring that 'if net.IP.IsPrivate, then the host at address is trusted', which is generally not a safe assumption." The same maintainer points out CGNAT range membership does not say an address is being used for CGNAT. https://github.com/golang/go/issues/76067 . Q1. C. HL.
- Open proposal 79925 (undated) to document that `IsPrivate` misuse "yield[s] a steady stream of high-severity CVEs", and that IPv4-mapped and transition addresses (6to4, Teredo, NAT64) are not covered. Python's `ipaddress` takes the opposite call on CGNAT (`is_private` false). https://github.com/golang/go/issues/79925 . Q1. C. HL.
- Real bug: memos SSRF guard used `IsLoopback||IsPrivate||IsLinkLocalUnicast||IsUnspecified`, so the RFC 6598 shared range passed as public (Alibaba metadata a cloud metadata address in that range and Tailscale hosts reachable). https://github.com/usememos/memos/issues/6099 (undated, an incomplete fix of CVE-2024-29028 and CVE-2025-22952). Q1. B. HL.
- **Inference** for a private-peer allowlist: parse `RemoteAddr` with `netip.ParseAddrPort`, call `.Unmap()` (IPv4-mapped IPv6 otherwise slips past v4 prefixes), strip zone, then test explicit prefixes: loopback, the three RFC 1918 ranges, the RFC 6598 shared range minus a ChromeOS slice of it if wanted, the ULA range (RFC 4193) (covers Tailscale ULA), IPv6 link-local only if you want link-local. Build it from named prefixes, not `IsPrivate`.

What breaks it (**Inference**, with sources in section 6):
- Rootless podman default port forwarding, Docker userland proxy and same-host proxies rewrite the peer to a private or loopback address, so an internet request passes the check.
- A router with port forwarding to the host passes internet traffic with the real source, so the check works there; the check is blind to a hostile device on the LAN or inside the tailnet (shared nodes, a compromised phone).
- CGNAT ISPs and some mobile networks can hand a device a the RFC 6598 shared range address that is not a Tailscale address; a plain prefix test cannot tell them apart. WhoIs can.
- Link-local and ULA ranges are reachable from any host on the same L2 segment.

## 5. X-Forwarded-For and trusted-proxy rules

- Caddy: "By default, no proxies are trusted." Trusted requests get the client IP parsed from headers, default `X-Forwarded-For`, parsed left to right. `trusted_proxies_strict` (v2.8) parses right to left; "the left-most IP address may be spoofed by the client" when HAProxy, Cloudflare, ALB etc. append. `private_ranges` expands to `the RFC 1918 ranges, loopback, part of the ULA range and ::1` (so it does NOT include the RFC 6598 shared range or the whole ULA range). https://caddyserver.com/docs/caddyfile/options . Q1. V. HL.
- Caddy `reverse_proxy` ignores incoming `X-Forwarded-*` from untrusted peers; warns that Cloudflare can leave `X-Forwarded-For` spoofable. https://caddyserver.com/docs/caddyfile/directives/reverse_proxy . Q1. V. HL.
- Caddy forum: with a Cloudflare tunnel Caddy sees the other container as the peer, so `trusted_proxies cloudflare` does nothing; the advised fix was `static private_ranges`, which then trusts every container on the network. A maintainer also warns that trusting a whole tailnet range plus `Cf-Connecting-Ip` lets any exposed proxy on the tailnet forge it. https://caddy.community/t/cloudflare-remote-ip/23841 (2024-05-15), https://caddy.community/t/cloudflare-proxy-x-forwarded-for-client-ip-issue/25154 (2024-08-11). Q1. C. HL.
- Traefik: untrusted peers get inbound `X-Forwarded-*` deleted, trusted ones are kept; `forwardedHeaders.insecure` "always trust ... only for tests". The trust decision is at the entrypoint. Traefik also lists CVE-2026-35051 (a spoofed prefix honoured with trust off) and CVE-2026-54764 (ForwardAuth trusting a spoofed port) as decided issues in this class. https://doc.traefik.io/traefik/reference/install-configuration/entrypoints/ ; https://doc.traefik.io/traefik/master/contributing/security-decisions/ ; code: https://github.com/traefik/traefik/blob/master/pkg/middlewares/forwardedheaders/forwarded_header.go . Q1. V/B. HL.
- Cloudflare appends the visitor IP to any inbound `X-Forwarded-For`: a client sending `a,b,c` arrives as `a,b,c,<visitor>`; Cloudflare recommends `CF-Connecting-IP`. https://developers.cloudflare.com/fundamentals/reference/http-headers/ ; reproduction https://github.com/cloudflare/cloudflared/issues/1426 . Q1. V/C. HL. A consuming app that takes the leftmost XFF is spoofable: https://github.com/TemujinCalidius/FediHome/issues/109 and https://github.com/matrix-construct/tuwunel/issues/427 (both undated). C.
- Cloudflare Tunnel: nginx behind `cloudflared` saw the peer as `127.0.0.1`; to recover the client the operator had to add 127.0.0.1 to the trusted list (`set_real_ip_from 127.0.0.1`). https://community.cloudflare.com/t/real-ip-using-argo-tunnel-and-nginx-proxy-manager/355271 (2022-02-09). Q1. C. HL.
- One app (Aivory) trusts XFF only when the direct peer is loopback or private, and then takes the rightmost non-private entry: the pattern that fails open if the proxy is exposed some other way. https://docs.aivorygo.com/docs/deployment/cloudflare-proxy/ (undated). C. HL.

**Inference** for Meat Mode:
- Default: trust no forwarding headers. Decide privacy from the TCP peer only.
- If a reverse proxy at the user's own domain is supported, make "trusted proxy" an explicit list the operator sets; with a trusted proxy, require the PROXY protocol or the rightmost-untrusted XFF walk, and still require the original client to fall in the private allowlist.
- A tunnel that dials from the same host (Cloudflare Tunnel, Serve proxying to loopback) makes peer = loopback for everyone. In that shape a loopback peer proves nothing, so loopback must not count as private unless the operator declares "my only proxy is X".

## 6. What breaks each technique (container and proxy shapes)

- Docker published ports: external clients keep their address (kernel DNAT), but traffic through `docker-proxy` shows the bridge gateway: host-to-`127.0.0.1` and IPv6 clients on an IPv4-only bridge appear as the gateway address. "An allow-list containing `the Docker bridge gateway` grants admin access to every container that can reach the published port". https://runbook.academy/courses/docker/lessons/docker-published-ports-userland-proxy/ (2026) C; https://github.com/caddyserver/caddy-docker/issues/406 C; official: https://docs.docker.com/engine/network/port-publishing/ , publishing `-p 8080:80` listens on all host addresses and is "insecure by default", use `127.0.0.1:` to restrict; releases before 28.0.0 let same-L2 hosts reach localhost-published ports (moby issue 45610). V. HL.
- Rootless podman (this host uses it): bridge networks forward through `rootlessport`, "a userspace proxy that does not preserve client source IPs". Podman docs: pasta (the rootless default network) "keeps the original source address" on port forwarding. Experimental `rootless_port_forwarder="pasta"` fixes bridge networks and needs recent passt. A Podman issue (opened 2026, closed 2026-09-07 by a maintainer: "already implemented in podman 6") describes Traefik logging an internal bridge address for a public request. https://github.com/podman-container-tools/podman/blob/main/rootless.md ; https://docs.podman.io/en/stable/markdown/podman-pod-create.1.html ; https://github.com/podman-container-tools/podman/issues/29727 ; https://rootlesscontaine.rs/how-it-works/netns/incoming/ . V/C. HL. **Inference**: whichever engine runs the hub, test the real path (curl from another machine) and read `RemoteAddr` in a debug endpoint before relying on it. A config that works under pasta mode silently breaks on a bridge network.
- Same-host reverse proxy or tunnel (Caddy, nginx, cloudflared, Serve): peer is loopback or a container address for every request, see sections 1 and 5.
- Tailscale Serve to loopback: peer is loopback for every request including Funnel; only headers (or PROXY protocol on TCP mode) carry the origin. See section 1.
- Cloudflare Tunnel: loopback or container peer; real client only in `CF-Connecting-IP`/XFF, which are trustworthy only if nothing else can reach the hub. See section 5.
- Host firewall or Tailscale ACLs: not a detection method but the boundary itself; listening on a Tailscale address only (bind to the node's 100.x or use tsnet) removes the loopback ambiguity.

## 7. Startup check: does the public URL resolve only to private addresses?

- Funnel publishes public DNS: "When you turn on Funnel, we create public DNS records for your `<node>.<tailnet>.ts.net` name that points to a set of ingress servers". Before Funnel, Tailscale did not resolve `ts.net` names for outsiders. https://tailscale.com/blog/tailscale-funnel-beta (2023-03-30). Q1. V. HL.
- Non-Funnel node names resolve inside the tailnet via MagicDNS (the Tailscale's in-tailnet resolver address resolver) to tailnet addresses. https://tailscale.com/docs/reference/dns-in-tailscale (HL). On a tailnet member, MagicDNS answers `*.ts.net` locally even for a Funnel hostname, so the check below passes while the name is public. https://tailscaleproxy.vercel.app/troubleshooting (undated, third-party). C. HL.
- Stale public records: a 2026-10 report says authoritative servers kept serving ingress addresses about 4 hours after Funnel was turned off, and a later comment says an active Funnel node's records were withdrawn for about 12 hours (so the DNS state is also unreliable in the other direction). https://github.com/tailscale/tailscale/issues/21746 (2026-10-10 to 2026-10-16); also https://github.com/tailscale/tailscale/issues/21698 (NODATA for a live Funnel). Q1. C. HL.
- Tailscale itself says publishing public DNS records that point to Tailscale IPs is "relatively harmless"; a public record to a private address is normal for a custom domain. https://tailscale.com/docs/reference/dns-in-tailscale . V. HL.
- **Inference** for a startup check on a configured public URL host: (1) resolve through a public resolver that bypasses local MagicDNS (a configured DoH/UDP resolver, not the system one); (2) refuse to start in "private" mode if any returned A/AAAA is outside the private allowlist (this catches Funnel ingress addresses and a custom domain pointed at a public IP); (3) NXDOMAIN or NODATA from public DNS is acceptable for a tailnet name; (4) also resolve with the system resolver and require that result to be private; (5) re-run on a timer, log loudly, and keep it as a warning plus a refusal for the unauthenticated modes only. It cannot see split-horizon DNS at the user's router, DNS rebinding, or a later switch to Funnel. It is a misconfiguration alarm, not a boundary. It also needs egress DNS from the hub.
- Also read the hub's own Tailscale state if present (`tailscale serve status --json`, or LocalAPI) to detect Funnel config on the hub's port: Funnel and Serve cannot share a port. Not tested here.

## 8. Recommended stack for the private-only guard (all **Inference**)

1. Primary: listen only on the intended interface (loopback behind Serve, or the node's tailnet address, or tsnet). Do not rely on a code check if a bind can enforce it.
2. Check per request: direct peer must be in the named allowlist; if behind Serve require a non-empty `Tailscale-User-Login` and reject any request carrying `Tailscale-Funnel-Request`; if tsnet, require WhoIs success.
3. Ignore all `X-Forwarded-*`, `Forwarded`, `X-Real-IP`, `CF-*` unless the peer is in an explicit trusted-proxy list; then use rightmost-untrusted rules.
4. Startup: DNS check and a self-test that reports what peer address the hub actually sees through the published port.
5. Treat all of the above as one layer; the password stays mandatory when the boundary cannot be proven (see Q3).

## Gaps

- Did not test Serve/Funnel behaviour live, so "Funnel sets the marker, Serve does not" rests on source plus vendor docs. The kb page says Funnel has no identity headers and does not mention the marker; the marker comes from code and one third-party page.
- No count of internet-exposed Tailscale-fronted hubs (that is Q2).
- I did not find a Go library for "trusted proxy" parsing that I could vouch for; Caddy and Traefik code are the reference implementations.
- Podman 6 behaviour beyond the issue and docs excerpts was not verified; the host's installed version was not checked.
