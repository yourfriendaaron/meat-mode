# Cluster B: attachment storage on a Go + SQLite server

Searched with Exa (about 9 calls). "Read" means Exa returned the page text I used; most fetches were capped at a few thousand characters, so I mark them "highlights only" unless the page was short. Publication dates are given where Exa gave one, else "n/d" (no date shown). Grades: A controlled/large n, B single team/small n, C anecdote/opinion, V vendor guidance. Conclusions marked **Inference**.

## Q1 Files vs BLOBs in SQLite

1. SQLite, "Internal Versus External BLOBs". https://sqlite.org/intern-v-extern-blob.html (page last updated 2022-04-18; tests from 2011 on ext4, SQLite 3.7.8). Quote: "For BLOBs smaller than 100KB, reads are faster when the BLOBs are stored directly in the database file. For BLOBs larger than 100KB, reads from a separate file are faster." Also "A database page size of 8192 or 16384 gives the best performance for large BLOB I/O." Tests used 10KB to 1MB blobs only, about 100MB total per case. Update on the page: SQLite 3.19.0 "about 35% faster than direct disk I/O for both reads and writes of 10KB blobs". Answers Q1. Grade B (single vendor, small blobs, old hardware, self-warned "your mileage may vary"). Page text read in full.
2. SQLite, "35% Faster Than The Filesystem". https://sqlite.org/fasterthanfs.html (measured week of 2017-06-05). Quote: "a single SQLite database holding 10-kilobyte blobs uses about 20% less disk space than storing the blobs in individual files". Its own caveat: some reviewers saw SQLite slower, and SQLite does worse "when experiments are run using a cold filesystem cache". It also cites Jim Gray's SQL Server study: database wins below roughly 250KiB to 1MiB. Answers Q1. Grade B. Highlights plus first sections only.
3. SQLite, "Write-Ahead Logging". https://sqlite.org/wal.html (Exa date 2026-08-25). Quotes: autocheckpoint at "1000 pages (and is thus about 4MB in size)"; "Very large write transactions. A checkpoint can only complete when no other transactions are running... a large change to a large database might result in a large WAL file"; "As of SQLite version 3.11.0 (2016-02-15), the WAL file for a single transaction should be proportional in size to the transaction itself"; the checkpoint "does not normally truncate the WAL file (unless the journal_size_limit pragma is set)". Answers Q1 (WAL growth). Grade V (primary vendor docs). Highlights only.
4. Incremental blob API. https://sqlite.org/c3ref/blob_open.html (n/d). sqlite3_blob_open needs a rowid table and the column must hold a BLOB or TEXT; "The size of a blob may not be changed by this interface" (so you must insert a zeroblob of the final size first); a handle expires if the row is updated. Grade V. Read in full.
5. modernc.org/sqlite incremental blob I/O: I searched (two queries) and found no evidence that modernc.org/sqlite exposes sqlite3_blob_open. pkg.go.dev (v1.60.1, Exa date 2026-09-29) and the README highlights list virtual tables and vec, not blob I/O. By contrast ncruces/go-sqlite3 lists "incremental BLOB I/O" under advanced features (https://github.com/ncruces/go-sqlite3/blob/main/README.md, n/d, grade V), and the mattn/go-sqlite3 issue #239 (open since 2015) notes database/sql has no blob handle type (https://github.com/mattn/go-sqlite3/issues/239, updated 2025-10-17, grade C). **Inference**: with modernc under database/sql, a BLOB read or write holds the whole value in a Go []byte, so a 25 MB attachment costs about 25 MB of memory per request plus the same again in WAL pages. This is unverified against the modernc source; check `rg -n "blob_open" ` in the module before relying on it. Gap: I did not read modernc's source.
6. Memos exposes DB storage as a documented default with the tradeoffs "larger database size, heavier database backups, less attractive for media-heavy instances" (see Q2 item 2).

**Inference for Q1**: Meat Mode attachments (photos, PDFs, a few KB to ~25 MB) sit mostly above SQLite's 100KB crossover. With one SQLite connection and WAL, a 25 MB blob write is one 25 MB transaction that blocks every other write and leaves a WAL of about 25 MB until a checkpoint plus truncation. Files in the data directory avoid that and keep the DB small, but need their own backup and consistency story (Q4). A hybrid (small blobs in DB, large in files) buys the SQLite-measured speedup only for sub-100KB files and doubles the code paths; not worth it for one user.

## Q2 How comparable self-hosted apps store uploads

1. Vikunja. https://vikunja.io/docs/config-options/ (n/d) and source config.go (https://github.com/go-vikunja/vikunja/blob/d604d8d4/pkg/config/config.go). Quotes: `files.maxsize` "Default: 20MB"; `files.basepath` "Default: ./files"; `files.type` default `local` (S3 optional); `service.enabletaskattachments` default true. Files on disk, metadata in the DB. A community thread (https://community.vikunja.io/t/attachment-size/65, 2020-08-08) shows the usual trap: a reverse proxy's `client_max_body_size` (nginx default 1MB) fails uploads before the app's cap applies. Answers Q2. Grade V (docs and source). Highlights only.
2. Memos. https://usememos.com/docs/configuration/storage (n/d). Three backends: database, local filesystem, S3-compatible. "Database-backed attachments are the default." Existing attachments keep their storage id; "switching the default does not move old files". Proto (https://github.com/usememos/memos/blob/6da8461e/proto/store/instance_setting.proto) has `upload_size_limit_mb` and `filepath_template` such as `assets/{timestamp}_{filename}`. A third-party API page (https://mintlify.wiki/usememos/memos/api/instance, n/d, grade C) states "Maximum upload size in megabytes. Default: 32"; I did not confirm 32 in Memos' own source. Answers Q2. Grade V except the 32 figure.
3. Joplin Server. https://discourse.joplinapp.org/t/max-attachment-size-when-syncing/30689 (2023-05-06) quotes server code `itemSizeHardLimit: 250000000, // Beyond this the Postgres driver will crash the app`. Joplin Cloud plans (https://joplinapp.org/plans/, n/d, grade V): 10 MB per note or attachment on Basic, 200 MB on Pro, unlimited on self-hosted Business. Joplin Server stores items in its database, and the cap exists because of that. Answers Q2. Grade C for the forum quote, V for the plans.
4. Trilium (TriliumNext). https://github.com/TriliumNext/Trilium/blob/main/docs/User%20Guide/User%20Guide/Basic%20Concepts%20and%20Features/Import%20%26%20Export.md (n/d): before v0.104.0 the upload limit was "250 MiB"; now a single item is capped at "approximately 374 MiB" by the sync protocol; import memory "will remain somewhere around the 2 gigabyte mark". Issue #4718 (https://github.com/TriliumNext/Trilium/issues/4718, 2024-03 to 2025-08): the author said "Trilium is not designed as a 'huge file storage'"; a 1GB file failed with "The bound string, buffer, or bigint is too big". Attachments live in its SQLite DB, loaded whole into memory. Answers Q2. Grade V for docs, C for the issue thread.
5. Paperless-ngx. https://docs.paperless-ngx.com/faq/ (n/d): documents are plain files in a media directory, "Paperless-ngx never modifies your original documents. It keeps checksums of all documents and uses a scheduled sanity checker". Its config page has no upload-size setting; the nginx proxy was the blocker in discussion 4496 (https://github.com/paperless-ngx/paperless-ngx/discussions/4496, 2023-11-03, grade C). Grade V/C.
6. Nextcloud Deck. https://help.nextcloud.com/t/max-upload-size/71839/3 (2021-04-10): "Starting with Deck 1.3.0 new attachments are completely handled by the files app - so the default Nextcloud limitations are counting now." Files on disk under the app data folder. Grade C (forum answer by a maintainer).
7. Actual Budget. Issue #8575 (https://github.com/actualbudget/actual/issues/8575, 2026-07-27): Actual "does not appear to have first-class transaction attachment support". Nothing to copy. Grade C. A third-party Nextcloud budget app (https://budget.otherworld.dev/docs/nextcloud-integration.html, n/d, grade C) sets receipts "up to 25 MB" and notes its export does not include receipt files.

**Inference**: of six apps with attachments, Vikunja, Paperless, Deck and Memos (optionally) use the filesystem; Joplin Server and Trilium keep blobs in the DB and have hit hard memory or driver limits around 250 to 400 MB. The common per-file caps are 20 to 32 MB (Vikunja 20MB, Memos about 32MB), matching the 25 MB target. No source gave a default total cap. Gap: Joplin Server's and Trilium's actual DB column layout was not read.

## Q3 Serving uploads from the same origin

1. web.dev, "Securely hosting user data in modern web applications", David Dworken. https://web.dev/articles/securely-hosting-user-data (n/d, Google). For inactive content (not HTML/JS), no separate domain is needed if you set: a safe `Content-Type` ("When in doubt, `application/octet-stream`"), `X-Content-Type-Options: nosniff`, `Content-Disposition: attachment; filename="download"`, `Content-Security-Policy: sandbox`, `Content-Security-Policy: default-src 'none'`, `Cross-Origin-Resource-Policy: same-site`. Their claim: this gives "a high degree of confidence" against injection. For active content (HTML, SVG) they say the simplest option is CSP `sandbox`, and the full fix is a separate sandbox domain on the public suffix list. Answers Q3. Grade V (vendor security team guidance). Highlights only.
2. MDN nosniff. https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Content-Type-Options (2026-03-17): nosniff stops "user-uploaded content" being run as HTML when the type is wrong or missing. Grade V. Highlights.
3. MDN Content-Disposition. https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Disposition (n/d): `attachment` triggers a download; `inline` is the default; send both `filename` and `filename*=UTF-8''...`; avoid percent escapes in `filename` ("Firefox and Chrome decode them, while Safari does not"). Grade V.
4. MDN CSP sandbox. https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/sandbox (n/d): a bare `sandbox` gives the resource an opaque origin ("The Origin of sandboxed resources without the allow-same-origin keyword is null"), blocks scripts and forms. Widely available since 2016-11. Grade V.
5. Worked example of SVG handling: PocketPaw PR #1475 (https://github.com/pocketpaw/pocketpaw/pull/1475, n/d). SVG is kept out of the inline list, served with `Content-Disposition: attachment`, nosniff and `default-src 'none'; style-src 'unsafe-inline'; sandbox`, with a regex sanitizer as defence in depth only. Grade C (one project's PR; it asked reviewers whether this is enough).

**Inference** for Meat Mode (the app CSP already allows only `img-src 'self' data:`, so the page itself cannot be scripted by an `<img>`): serve every file from one handler with `nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, a stored (not client-trusted) content type, and `Content-Disposition: attachment` by default. Allow `inline` only for an allowlist the server verified by sniffing the first 512 bytes (`http.DetectContentType`): PNG, JPEG, GIF, WebP, and maybe PDF. Never inline SVG, HTML, XML, or anything unknown (send `application/octet-stream`). Inline PDF is the one judgement call: the sources do not settle it, and a sandboxed PDF may not render in some browsers. Rendering images through `<img src="/api/...">` is covered by `img-src 'self'` and runs no script even for SVG, but a direct navigation to an SVG would run script, hence the header set above. Gap: no source tested current browser behaviour for CSP sandbox with PDF viewers.

## Q4 Atomic writes and orphan cleanup

1. Build Your Own Database From Scratch in Go. https://build-your-own.org/database/01_files (n/d). Pattern: write to a temp file opened with `O_EXCL`, `fsync`, `rename`, and note that "SaveData2 is readers-writer atomic, but NOT power-loss atomic" until the parent directory is also fsynced. "Both creating a file and renaming a file update the containing directory." Grade C (tutorial, but consistent with POSIX). Highlights only.
2. pg_hardstorage fsutil. https://github.com/cybertec-postgresql/pg_hardstorage/blob/main/internal/fsutil/fsutil.go (n/d): "POSIX is explicit: fsync(fd) flushes the file's content and inode but NOT the parent directory. An unflushed parent directory can cause a successful rename() to vanish on power loss." Full sequence: tmp, write, `Sync`, `Close`, `Rename`, fsync of the directory. Grade B (one team's code and comments).
3. cplieger/atomicfile. https://github.com/cplieger/atomicfile (n/d): same sequence; "A process killed before the rename leaves its temp file behind. Nothing in the package removes it on its own, so call CleanupStaleTemps at startup or on a schedule." Notes `*os.Root` variants to block symlink or `..` escapes. Grade B.
4. Scenery atomicfile (https://github.com/scenery-sh/scenery/blob/v0.3.6/internal/atomicfile/atomicfile.go, n/d) uses `os.CreateTemp(dir, "."+base+".tmp-*")` in the same directory, which guarantees the rename stays on one filesystem. Grade B.

I found no authoritative document (Go team or SQLite) that prescribes orphan cleanup for file-plus-DB designs. **Inference**, the usual shape:
- Upload: stream the body (cap with `http.MaxBytesReader`) into `data/attachments/tmp/<random>` while hashing with SHA-256, `Sync`, rename to `data/attachments/<sha256 or id>`, fsync the directory, then insert the DB row. A crash between rename and insert leaves an orphan file, never a row pointing at nothing.
- Delete: delete the row first, then the file; a crash leaves an orphan, again not a dangling row.
- Startup sweep: remove everything in `tmp/` older than a grace period, and list files with no row and rows with no file; log the missing-file rows rather than deleting them. Content-addressed names make a duplicate upload idempotent but need reference counting on delete.
- Back up with SQLite's online backup or `VACUUM INTO` for the DB, and copy attachments after it so every row's file exists (rows first, files second would risk the opposite).

## Summary of strength

Strongest: SQLite's own 100KB crossover (B), SQLite WAL doc on large transactions (V), web.dev header set for user content (V), Vikunja 20MB default and local-file storage (V), the fsync-the-directory requirement (B). Weakest: modernc blob I/O (not found), Memos' 32MB default (C), all inline-PDF safety.
