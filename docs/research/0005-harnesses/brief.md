# Reader brief: agent harnesses beyond Claude Code (meat-nv6.3)

Context: Meat Mode is a self-hosted to-do app for one person. A bridge on the agent machine can start a coding agent on a task when the person taps "Ask agent": it runs the agent headless in the task's repo, gives it a first prompt, shows a short activity line ("Editing notes.txt", "Running go test") from the agent's tool calls, lets the person add a note that goes into the live run, enforces a wall-clock timeout and a spending cap, and resumes the same agent conversation on the task's next ask. Today it runs Claude Code only: `claude -p --input-format stream-json --output-format stream-json --verbose --replay-user-messages --permission-mode auto`, plus `--max-budget-usd N` and `--resume <session_id>`. It reads `session_id` from stream lines, `assistant` lines' `tool_use` blocks for the activity line, `rate_limit_event` and the final `result` line (is_error, subtype containing "budget", total_cost_usd). A note on a live run is written to stdin as a stream-json user line; stdin is closed after the last turn so the process exits. It strips `CLAUDECODE` and `CLAUDE_CODE_*` from the child's env. The bridge is about to grow a harness interface with Claude Code as one implementation and Codex, OpenCode, Gemini CLI and Pi as others. The agent runs unattended: nobody can answer a permission prompt.

The questions, in priority order (spend most effort on the first):
Q1 For your cluster's harness, the exact non-interactive command line: the flags for headless/print mode, structured (JSON or JSONL) output, the event types in that stream with real examples (session start, assistant text, tool call with its tool name and input, tool result, final result or turn end, errors, usage or rate limits, cost), and the exit codes.
Q2 Sessions: where the session id appears in the output, how to resume or continue that session from a later non-interactive run (flag and exact syntax), and where sessions are stored.
Q3 Sending a follow-up message into a run that is still going: does it read more user messages from stdin (a streaming input format), a server or RPC mode, or nothing (then the only option is to queue the message and resume after the turn ends)?
Q4 Limits and permissions: a spending cap, a turn or step cap, a timeout; how to run with no approval prompts (auto-approve or sandbox modes) and which mode is closest to "edit files and run commands in this repo without asking"; the tool names it uses for shell, edit, write, read, search, web.
Q5 Environment: variables it sets in its own child processes (so a nested run can detect it) and variables a child started from inside one of its sessions should not inherit; the instruction file it reads (AGENTS.md, GEMINI.md, ...); how it is installed and signed in; current version, last release date, stars.
Q6 Known problems in headless use: hangs waiting for input, output format changes between versions, resume bugs (issues with numbers and dates).
